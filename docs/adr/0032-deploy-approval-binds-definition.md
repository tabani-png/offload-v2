# 0032. Deploy approval binds a readable definition

Status: accepted · Date: 2026-11-14

## Context
The deploy approval bound `artifact_sha256` and `receipt_hash`, hashes the user cannot read. The second OK must be an
informed OK: what triggers it, what it can do, on which account, within which limits ([design review C (2026-11-14)](../SOURCES.md#design-review-c), P1(2)).

## Decision
- `definition_hash = sha256(JCS(resolved routine.json))`. The resolved definition covers the trigger, every step's
  class, capability and `runs_on`, every connection id with its provider and account label (which account), each
  tool pin hash ([ADR 0033](0033-pinned-connector-resolution-and-launch-catalog.md)), and the limits (items per run,
  runs per day, run budget, quiet hours, recipients source).
- The deploy approval (`POST /v1/builds/{id}/deploy`) binds **`artifact_sha256`, `receipt_hash` and `definition_hash`**.
  Any mismatch is `403 hash_mismatch`.
- Before the second OK, the Mac and web UI render the definition in words, for example (illustrative): "Every Monday 9:00. Reads Stripe payouts
  (stripe · acme-live). Appends rows to the Finance sheet (google · your Workspace account). At most 50 rows a run.
  Asks before each batch." The words are generated by code from the definition, not by a model.
- `routine_versions.definition_hash` stores it; a changed definition is a new version and needs a new deploy approval.

## Consequences
- The user approves what will run, in words, and the hash makes the words binding.

## Alternatives considered
- Bind only artifact and receipt hashes (the previous version): not readable.
