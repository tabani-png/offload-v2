# m5-01-understanding

## Summary
The hard break found by the end-to-end test of `main` on stand-in data (2026-11-22, report kept outside the repo, top
fix 1): observations
land in Postgres and `observations.ingested` is written to the outbox, but nothing reads them, so the brain's
`runMemberUpdate` (p43a/p43b) has no producer and the stored OCR and Accessibility text never reaches it. This slice
builds **understanding** ([ARCHITECTURE section 5](../../docs/ARCHITECTURE.md#5-cloud-brain-and-user-model)):
sessionize, describe spans from the masked text (rules first, the `label` route optional and injected), embed with a
deterministic local embedder, induce tasks and instances, and hand the result to `runMemberUpdate` as an
**understanding window**. It moves the M5 exit criterion "Today shows one ranked suggested fix from observed work"
(the finder needs task keys with instances) and ROADMAP acceptance `SPAN`, `LEDGER` (fixture weeks) and `INDUCE`.

  through `runMemberUpdate`; span embeddings are not stored (Scope changes).
- Exported from `@offload/brain` (`services/brain/src/index.ts`), for m5-04 and m1-06:
  - Types `UnderstandingWindow`, `WindowSpan`, `WindowTask`, `WindowInstance` (unchanged shape, `src/user-model/ports.ts`,
    now documented as produced by `buildUnderstandingWindow`).
  - `buildUnderstandingWindow(input, deps?) → Promise<UnderstandingWindow>` where
    `input = { timezone, days: DayLabel[], observations: CaptureObservation[], texts: CaptureText[] }` and
    `deps = { embedder?: Embedder, labeler?: SpanLabeler }`. Pure apart from the injected ports.
  - `CaptureObservation { device_id, object_id, ts (epoch ms), kind, app_bundle_id, app_name, title, host, doc, keys,
    clicks, source, import_id }` and `CaptureText { device_id, object_id, ts, text, text_source, app_bundle_id }`
    (the `observations` / `observation_texts` columns of DATA_MODEL section 5; nulls for absent fields).
  - `Embedder { id; dims; embed(texts): Promise<number[][]> }`, `localEmbedder()` (`local:hash:1024`).
  - `SpanLabeler { label(items: { span_id, text }[]): Promise<Map<span_id, { verb?, object? }>> }`; only values in
    `SPAN_VERBS` / `SPAN_OBJECTS` are used. `routerSpanLabeler(route, { tenant_id, member_id })` builds `label` route
    calls with a label-only schema and `untrusted()`-wrapped text (m5-03 router call contract); never called in tests
    against a real provider.
  - The job: `runUnderstanding(deps, event) → UnderstandingResult` and `drainUnderstanding(deps, { tenantId, limit? })`
    (in-process consumer), `understandingWorkflow(deps)` (a `WorkflowFn` for the durable runtime, input
    `{ tenant_id, event_id }`), `pgCaptureStore(pool)`, `UNDERSTANDING_CONSUMER = "workflow:understanding"`.
    `deps = { capture: CaptureStore, runBrain: RunInTenant, clock: () => number, embedder?, labelerFor?, estimateFor? }`
    where `labelerFor(member)` builds the label route for the event's tenant and member (review 1).
    `UnderstandingResult.status` is `updated`, `duplicate` (already delivered: nothing read, nothing written),
    `busy` (another consumer holds the event's claim), `failed` (drain only; `error` is the recorded code),
    `empty` (no observations in range), `paused` (learning paused) or `unknown_member`.
- Event payload read: `{ device_id, member_id, seq, accepted }` as m3-01 writes it, plus optional `first_ts`,
  `last_ts` (API.md section 7 is corrected to say so).
- Constants (ARCHITECTURE section 5): minimum span 10 s, idle merge 15 min, idle backdate 120 s, embedding 1024 dims,
  assign threshold 0.7, instance gap 10 min, pseudonym link gap 20 min (person, email, phone) and none for `doc`,
  item pseudonym on at most 12 spans, transition within 2 min seen at least 2 times and on at least half of the
  step's spans.

## Design note
Pipeline, all in `services/brain/src/understanding/`:
1. **Read** (`capture.ts`, `pgCaptureStore`): inside `withTenant` as the event's member (principal `durable`, role
   `service`), so tenant RLS and the member wall apply. The range: `first_ts`/`last_ts` when the event has them, else
   the `ts` range of the member's rows whose partition `day` is the event's UTC day or the day before (rows just
   ingested: live rows have `day` = UTC date of `ts`, imported rows the ingest date). The range is widened to whole
   days in the member's timezone (from the brain profile), capped at 31 days ending at its last day, and every
   observation and text in it is read **by `ts`**, not by `day`. So an import is analysed on its own days and its
   records are anchored to its last day (m3-05 "ANCHOR").
2. **Sessionize** (`sessionize.ts`, written fresh after old `sessionize.ts`): segments end at the next focus,
   `idle_start` (backdated 120 s), `pause` or the last event; blips under 10 s join a contiguous neighbour; segments of
   the same app + title + host merge across idle up to 15 min. Text snapshots attach to the segment open at their `ts`.
3. **Cues** (`cues.ts`; app names only at the start of the first two lines of a snapshot): a segment on a **stand-in app** (`recording.unknown`, `screenwatch.screen`, app name `Screen`: what
   the recordings import emits without a macOS menu bar) takes its host from host tokens in its masked text (URL bar)
   and its app from known app names in window chrome text, before merging. A stand-in segment with no cue never merges
   across idle, so unrelated recordings stay apart.
4. **Describe** (`describe.ts`): verb and object from fixed vocabularies counted in the masked title and text
   (`SPAN_VERBS`, `SPAN_OBJECTS`), else a default verb by kind of work; pseudonyms (`<doc:h_…>`, `<person:h_…>`,
   `<email:h_…>`, `<phone:h_…>`) from the focus `doc`, title and text; content words (letters only, no digits, no
   tokens). The optional labeler fills verb/object only where the rules found none. A stand-in span with no cue and no
   words is **not joinable**: it counts as time but joins no task.
5. **Embed** (`embed.ts`): feature hashing of surface words, verb, object and content words (stemmed words weight 1,
   bigrams 0.5), signed buckets, 1024 dims, unit norm. Same text, same vector.
6. **Induce** (`induce.ts`): steps join by exact `app|host|verb|object` key when that key names an object or a verb
   read on screen on a named surface (review 1: a default verb with no object, or a stand-in without a cue, says
   nothing about the work), else the best step on the same surface with cosine ≥ 0.7. Tasks are connected components of steps linked by a shared item pseudonym or a reliable
   transition. Instances split on a new day, a gap over 10 min, a step coming back with a conflicting `doc` or the instance's first
   step recurring after another step. Ids are deterministic (uuid from sha256 of device and object ids), so the same
   observations give the same window and `runMemberUpdate` writes the same rows.
7. **Job** (`job.ts`): claim the event (session advisory lock in `withEventLock`; a second consumer gets `busy`) →
   duplicate check on `outbox_deliveries` → profile timezone (brain transaction) → read (capture transaction) → build
   the window (no transaction; the labeler's model call happens here) → `runMemberUpdate` after `repo.lockProfile`
   (brain transaction: one member's updates run one after the other) → mark delivered (capture transaction). A
   failure records `attempts` and `last_error_code` and rethrows; the drain records it as `failed` and goes on; after
   `MAX_ATTEMPTS` (5) the event is no longer pending. A re-run after a crash rebuilds the same window, which
   `runMemberUpdate` stores idempotently. A delivered event is never processed again.

Privacy: only masked C1 text is read; logs and errors carry ids and codes only. Task names are built from verb,
object, app and masked title words, never from snapshot text, and are scrubbed again by the user model (`safeName`). No model call unless a labeler is injected; the labeler goes through the router.

## Scope changes
- **Event payload**: API.md section 7 said `observations.ingested` carries `{ device_id, member_id, count, first_ts,
  last_ts }`; m3-01 writes `{ device_id, member_id, seq, accepted }`. services/api is out of scope here, so the
  consumer finds the range itself (Design note step 1) and uses `first_ts`/`last_ts` when present. API.md is corrected.
- **Span embeddings are not stored**: ARCHITECTURE says embeddings are stored in pgvector. The window carries task
  centroids, which the ledger stores (`task_ledger.centroid`, `real[]` until pgvector). A span-level vector table
  waits until something reads it (M7 entity resolution).
- **EMBED red test example changed after the red commit**: the "alike" pair shared 5 of 8 words (cosine 0.63, below
  the 0.7 assign threshold), which is not what two instances of one step look like; it now differs by the words one
  frame shows more (cosine above 0.7). The embedder was not tuned to the test.
- **Conflicting doc pseudonym, made precise** (INDUCE red test case changed after the red commit): an instance splits
  when a step already in it comes back with a disjoint `doc`, not on any two different docs. Live capture sends the
  pseudonym of each page's URL path as `doc`, so a mail message and the web form it leads to always differ; splitting
  on that would cut every live multi-step workflow into single steps. The test case is now `A(d5) B(d5) B(d6)` →
  `AB`, `B` instead of `A(d5) B(d6)` → `A`, `B`. Step B's title now names its order (`Order <doc:…>`), as A's does,
  so two B pages are two spans (same app, title and host would correctly be one span).
- **Old understanding code is written fresh, not copied**: old `describe.ts`/`induce.ts` depend on frame notes,
  grouping and the name masker; v2 gets masked text only, so the rules are smaller. Same constants.

Known limits (for m1-06 and later):
- Each event re-reads its whole days, so a live member whose Mac uploads every few minutes re-analyses today and
  yesterday per batch. Correct (idempotent), but `offload serve` should run the drain on a tick, not per insert.
- Imports and live data interplay (review 1 finding 9): imported rows carry today's partition `day`, so on an
  import's ingest day (and the day after) every live batch's fallback range also covers the whole imported range,
  up to 31 days, read into memory per event. m1-06 should coalesce a member's pending events (one run per member per
  tick) or have ingest write `first_ts`/`last_ts` into the event; both stay inside this consumer's contract.
- Each running event holds one pool connection for its claim (session advisory lock) besides its queries: size the
  `offload serve` pool for that.
- App cues use a fixed table of app names, read only at the start of a snapshot's first two lines; a recording of
  an app not in the table, or whose chrome OCR reads lower down, gets its host cue only.
- Instances split by the rules above; a workflow whose steps interleave with unrelated work inside 2 min can link
  through a transition only if it happens at least twice and on half of the step's spans.
